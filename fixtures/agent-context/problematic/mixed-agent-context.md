## Always-On Procedure

When reviewing an agent file, check the project purpose, supported inputs, commands, tests, docs, privacy posture, savings claims, warning labels, source body handling, fixture realism, browser compatibility, parser behavior, profile output, conversion output, smoke script coverage, release notes, public wording, and whether the document contains long procedures that should move into skills. Also compare repeated rules against nearby sections, look for vague phrasing that sounds precise but does not specify an action, inspect whether examples are doing real work, confirm that measured savings are not overstated, and note whether procedural detail is always-on or task-triggered. If the same section also explains how to build the UI, how to create release artifacts, how to author screenshots, how to structure onboarding, how to write every future warning category, and how to run every validation command, treat it as overloaded always-on context.

## Release, UI, Privacy, And Skill Workflow

When preparing release notes, summarize changed behavior and validation.

When drafting UI copy, show advisory warnings and measured savings.

When reviewing privacy posture, keep source document bodies local unless explicit approval exists.

When authoring skills, move deeper procedures out of always-on files.
